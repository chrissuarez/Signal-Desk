# Recommended Action is the system's routing field, decoupled from the user-owned Status

Ingestion previously overloaded `status`: a low `fitScore` wrote `status = DISMISSED`, conflating *what the system recommends* with *what the user has done with a role*. We decided to separate them cleanly. **`recommendedAction`** (resurrected from dead code, extended with a new `SUPPRESS` value: `ALERT | DIGEST | STORE | SUPPRESS`) is the system's computed routing decision, derived deterministically from the reconciled Strategic Category + Strategic Score + risk flags. **`status`** (`NEW | SAVED | DISMISSED | APPLIED`) becomes purely the user's lifecycle action, set only via the UI; ingestion no longer writes it.

The tier mapping reuses the brief's product-behaviour rules: STRATEGIC_FIT or high-scoring USEFUL_BRIDGE (with risks not HIGH) → ALERT; weaker bridges/ambiguous ops → DIGEST; SEO-comfort/generic/low-score/high-trap-risk → STORE; confirmed RESOURCE_ADMIN_TRAP / REJECT / pure-SEO / junior → SUPPRESS. `SUPPRESS` persists the row but hides it from default views — never deletes — so weight re-tuning can resurface it and the feedback loop keeps the signal.

Scope decision for the MVP: `ALERT` means **surface at the top of the dashboard**, not send a notification. The existing `notificationService` only `console.log`s; wiring real email/push is deferred to a later iteration. We chose this separation because user lifecycle and system routing change for different reasons and at different times — keeping them in one field made "the user dismissed it" and "the system suppressed it" indistinguishable, which breaks both filtering and any future learning loop.
